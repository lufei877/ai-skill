# 代码腐化与可维护性检查

“屎山”不是对作者或代码风格的评价。需要证明当前结构会增加哪些修改成本、隐藏什么错误或阻碍哪种验证；既看过度设计，也看缺少边界、状态与失败路径的混乱。

| 维度 | 检查方法与反证 |
| --- | --- |
| 职责与耦合 | 追一条业务变更从入口到存储的路径，查 UI 直连数据库、循环依赖、跨层访问私有状态、多个无关职责共用全局状态。长文件可能是内聚实现，短文件也可能造成跳转负担；以实际依赖和变更影响为证据。 |
| 单一事实源与重复 | 对逐字节重复候选和近似分支核对生成归属、业务语义、调用者；两处规则已漂移或同一变更必须多处手改才支持问题。测试夹具、平台必要分支、同源生成物不能自动判债。 |
| 抽象、依赖与兼容 | 检查只有透传的层、无人使用的扩展点、为小能力引入的依赖及过期适配；说明当前成本和已有使用者。抽象、DI、多层或 fallback 并非原罪；公共 API、schema、外部调用方和数据迁移先核实退出条件。 |
| 错误与降级 | 沿 catch/except、重试、默认值和备用实现追到用户可见结果；查丢失原因、伪造成功、无限重试、重试非幂等操作、资源未释放。合理降级应限定触发条件、有足够可观测性并维持输出契约；别把所有降级改为崩溃。 |
| 状态、并发与生命周期 | 检查重复状态源、旧响应覆盖新值、缓存失效、任务取消、组件卸载/进程退出、锁与事务、worker 重启。多份状态可能是明确投影，只有同步契约缺失或实际失效路径才构成发现。 |
| 类型和边界契约 | 检查绕过外部输入验证、断言掩盖空值/错误、跨层对象含义变化；类型通过不证明数据正确。依项目现有工具和语言约定判断，不为去掉一个 any 强制引入新验证库。 |
| 测试真实性 | 选关键正常/失败/权限/并发路径，对照断言是否验证用户可见行为，mock 是否遮住真正依赖/序列化/数据库边界，测试入口是否只枚举用例或依赖陈旧产物。mock 有隔离价值，测试少/覆盖率低本身不足以判定具体 bug。 |
| 可运行性与发布一致性 | 对照启动、配置、CI、打包入口、安装资源与源码版本；找失败入口、遗漏资源、文档命令与实际脚本漂移。开发阶段没有完整稳定发布流程不自动算缺陷，按当前交付契约判断。 |

候选问题尽量回答：改哪项业务会碰到它？哪些调用方受影响？已有保护或测试为何挡不住？最小局部修法是什么？怎样证明修后行为不变或故障消失？没有具体收益时保留观察或不报告。

修复建议优先消除已证实的危险路径与重复事实，再补关键验证，最后安排可独立交付的结构调整。按风险和依赖顺序分批，不默认全仓重写、替换框架或统一格式；工作量无法可靠估计时说明关键未知，不编造精确工时。
