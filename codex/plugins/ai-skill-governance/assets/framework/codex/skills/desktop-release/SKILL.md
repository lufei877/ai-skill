# Desktop Release — 桌面安装包正确性

## 目标与适用边界

建立或执行可追溯的桌面交付闭环：指定改动 → 固定源码 → 隔离构建 → 最终安装包 → 安装后验收 → 交付同一文件。支持 Electron、独立 Python 桌面应用及两者组合；Windows 优先，按项目支持矩阵适配其他系统。

用户只要求设计或审查时，交付方案或发现；授权接入时实现项目脚本与必要配置；要求打包时执行已有流程并补足检查。使用本 Skill 不等于已接入 CI，也不代表安装包验证通过。

默认接受 Electron 现有体积与安装器常规压缩。排除仅做体积优化、一般 UI/业务代码修改及纯 Web 服务部署。不要为复用本 Skill 迁移打包器、增加发布平台或启用工作流系统。

## 1. 识别现状与本次范围

先查入口脚本、锁文件、Electron builder/Forge 配置、Python 清单/spec、资源复制规则、已有 CI 和项目约定。确认软件形态、目标 OS/架构、安装方式、升级需求、签名策略及可用测试环境；这些事实能从代码查到时不追问。

查明会话共享同一目录，还是各自使用 worktree/分支。将本次需要纳入的改动列为清单，关联文件/提交和预期行为；会话完成消息只作线索，代码与集成测试才是证据。范围无法判断时只询问会影响本次交付的缺口，不要求所有历史会话都结束。

首次接入或更新项目契约时，读取 [项目接入与证据](references/project-contract.md)。多会话、未提交改动或发布来源不明时，读取 [源码快照与并行会话](references/source-snapshot.md)。

## 2. 固定输入，再允许构建

- 为本次运行指定唯一 `run_id`、负责人和隔离的构建/产物目录。多个打包任务不得共享输出或覆盖同一个候选包。
- 首选明确且完整的集成提交，在独立 checkout/worktree 构建；记录精确提交和源码内容指纹，不能用移动中的分支名代替。
- 用户要求包含未提交改动时，不擅自忽略、不替用户提交所有文件；按快照参考处理。普通递归复制正在变化的目录不构成可靠快照。
- 独立 worktree 的改动必须先集成并验证，再固定版本；共享目录则必须解决抓取快照期间的写入竞态。缺少稳定来源时暂停快照和打包，仍可完成资源审计与接入配置。
- 快照固定后，其他会话可继续开发。后来的改动属于下一次构建；需要纳入时创建新快照及新运行，重新执行受影响的验收。

## 3. 从快照构建候选包

复用项目现有命令，让本地和 CI 调用同一实现。记录实际工具版本、目标 OS/架构、依赖锁文件和影响行为的非敏感配置。CI 从明确提交检出；本地未提交文件不会自动进入远程 CI。

在本次隔离目录安装锁定依赖，按项目依赖关系重建主进程、preload、renderer 和适用的 Python 组件，再封装安装包。任一步失败停止后续步骤，禁止回退到历史 `dist`、旧可执行文件或上次安装包来维持“成功”。复用依赖下载缓存；不把其他运行的构建输出当作当前输出。

源码构建不要求安装包逐字节可复现：签名与时间戳可能不同。要求能追溯输入并验证行为；不能把“同提交”直接宣称为“完全相同的二进制”。

打包器若在构建步骤自动发布，先使用它支持的本地构建/禁止发布模式。用户授权发布时才执行对应的外部写入，已有授权持续有效。

## 4. 验收实际交付文件

读取 [安装包与运行验收](references/installed-validation.md)，按实际软件组件选择检查。至少核对：

1. 产物内容与本次版本一致，关键资源齐全，适用的 Python 组件属于本次构建。
2. 安装最终候选包，在隔离测试环境启动安装后的程序，核对实际可执行路径和构建编号。
3. 执行本次修改的验收场景以及受影响的关键业务链路，保存结果和日志。
4. 在支持的目标环境验证运行依赖；升级交付还要验证既有数据保留与迁移，使用测试数据副本。

窗口打开、源码测试通过、解包目录运行成功和安装包安装成功是不同事实。缺少目标测试环境时，明确未验证项和影响，不能把候选包标记为验收通过。已有正式发布标准继续适用。

### 常设安装包冒烟

已接入本 Skill 的项目，把最小安装包冒烟固化为可重复脚本，由本地和 CI 共用：安装候选包 → 从安装后路径启动 → 核对版本或构建号 → 走通一条不依赖真实账号的关键链路 → 正常退出并检查日志无未处理错误。每个发版候选包都必须通过该冒烟；它是发版的最低门槛，不代替上面按改动选择的验收。CI 没有桌面会话或缺少目标系统时，记为 `not_run` 并转到有交互桌面的测试环境，不能当作通过。

## 5. 绑定证据与交付

最终签名/封装完成后计算安装包 SHA-256。验收、证据记录、交付都绑定该文件；验收后的重建、重签名或重新封装形成新产物，须重新完成适用验收。内部 build-info 保存源码/构建身份；最终安装包哈希写入包外报告，避免自引用哈希。

区分 `built`、`artifact_checked`、`installed_verified`、`delivered`、`published` 五个事实，不让任何一个替代其他事实。失败保留阶段、命令、退出码和脱敏日志；修复后创建可区分的新运行。交付记录写清绝对路径、大小、哈希和验收范围，旧成功包与新失败运行不得混淆。

## 输出契约

按当前任务输出，不为设计任务伪造运行结果：

- **接入**：现有工具链与多会话模式、项目发布契约、实际脚本/CI 变更、已执行检查及未验证项。
- **打包**：`run_id`、源码快照、已纳入/未纳入改动、目标系统/架构、最终文件路径与 SHA-256、安装版身份及功能验证证据。
- **失败/诊断**：首个有效失败阶段、输入与产物身份、复现证据、最小修复和验证；未查证的原因标记为假设。
- **完成声明**：分别报告构建、产物、安装运行、交付与发布状态；检查未执行写 `not_run`，不适用写 `not_applicable` 并说明理由。
