# 工程取舍与演进边界

在依赖选择、兼容退役、迁移、重构或架构设计中，使用以下判断顺序。不要把任何一条当成脱离上下文的绝对命令。

## 1. 先建立现状证据

- 检查依赖清单和锁文件，确认项目是否已有可复用能力及实际版本。
- 搜索现有实现、调用方、公共契约、数据路径、测试和项目约定。
- 非简单或不熟悉的问题，先查官方文档和经过生产验证的成熟方案，再决定是否自行设计。
- 把外部资料视为候选证据；最终方案必须适配当前项目约束。

## 2. 选择最小且成熟的实现

理解真实流程后，按以下顺序判断；前一项能完整满足当前需求时停止，不为走完清单继续增加实现：

1. 这项行为是否确实需要存在，还是已有行为、配置或需求误解造成的重复工作。
2. 项目内是否已有经过验证的实现可以直接复用。
3. 标准库是否已经提供所需能力。
4. 当前平台或框架的原生能力是否已经覆盖。
5. 项目现有依赖是否可以完成，且不会破坏既有约定。
6. 是否可以用边界清晰的局部实现完成。
7. 以上均不合适时，再新增依赖、抽象或框架。

这个顺序不是以少写代码为唯一目标。涉及复杂协议、格式、安全、并发或长期维护时，成熟库可能比短小手写实现更可靠。新增库前至少评估：维护活跃度、安全记录、许可证、包体/启动/安装成本、目标平台与构建兼容、API 稳定性和未来替换成本。不要因为“成熟库优先”给小功能增加更大的依赖负担。

## 3. 从端到端最小闭环递增

- 先实现一条贯穿真实边界的最小可运行路径，而不是先铺设大批暂时未使用的抽象层。
- 为每个增量定义输入、输出和验证方式；保持现有可用面稳定。
- 先证明关键风险和集成点，再扩展分支、配置、性能和体验。
- 不把“先做 MVP”理解为可以跳过数据安全、错误可见性或必要迁移。

## 4. 用职责建立模块边界

- 让每类业务事实只有一个明确所有者，避免多个模块各自维护真相。
- 让模块通过清晰契约协作，保持依赖方向可解释。
- 仅在当前存在重复事实、变化轴或测试隔离需求时提取抽象。
- 不用文件数量衡量模块化，也不为假想复用提前建立框架。

## 5. 管理兼容路径生命周期

删除旧路径前，检查：

- 仓库内外调用方和用户；
- 公共 API、配置、文件格式和数据库 schema；
- 存量数据、升级顺序、迁移工具和回滚路径；
- 测试、遥测或真实使用证据能否证明已无人依赖。

确认未使用的内部兼容代码可连同测试和文档一起删除。仍有消费者或影响未知时，保留边界清晰的适配层，并记录负责人、退役条件和验证方式。修改公共 API 签名或数据库 schema 前必须获得用户确认。

## 6. 限制 workaround

- 优先修复已验证的根因。
- 只有外部系统限制、上游缺陷或明确时间窗口阻止根因修复时，才采用临时方案。
- 限制临时方案的作用域，记录原因、风险、测试、监控信号和移除条件。
- 不把 workaround 当作扩大无关重构或永久保留双路径的理由。

## 7. 支持长期演进

- 稳定公开契约、单一事实源和可替换的外部适配边界。
- 对真实变化设计迁移和版本策略，不为未被需求证明的未来写代码。
- 决策变化时更新或取代旧规则，避免兼容层和架构假设永久累积。

## 输出要求

在计划、实现说明或审查中，简要说明：采用了什么方案、复用了什么、排除了哪些高成本选择、兼容或迁移风险如何验证。仅在这些信息影响决策时展开。
