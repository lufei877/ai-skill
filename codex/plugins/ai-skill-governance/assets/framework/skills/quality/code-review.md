# 代码审查规范

## 什么时候读
审查代码、提交 PR、或用户要求 review 时加载。

## 规则
1. 检查是否违反 principles.md 的五项原则
2. 检查是否存在 constraints.md 中的禁止项
3. 关注：边界条件、空值处理、并发安全、资源泄漏
4. 变量/函数命名是否清晰表达意图
5. 是否有重复代码可以提取（但不过度抽象）
6. 测试覆盖关键路径
7. 涉及依赖、兼容、迁移或架构时，检查 engineering-decision-boundaries.md 的决策边界
8. 检查需求、Issue 和实现说明中的关键前提是否有证据支持，是否因迎合已有结论而跳过反证
9. 用户明确要求过度设计、YAGNI 或复杂度专项审查时，补充 complexity-review；它不替代本规范的正确性、安全、性能和范围检查

## 审查清单
- [ ] 改动是否超出需求范围（精准手术原则）
- [ ] 是否有过度设计（极简优先原则）
- [ ] 错误处理是否完整
- [ ] 是否有安全隐患（注入、XSS、硬编码密钥）
- [ ] 性能是否可接受（N+1 查询、大循环内 IO）
- [ ] 是否接受了未经验证的关键前提，或把合理推断、主观判断和未知写成已验证事实
- [ ] 重要数字和结论是否有适当证据；无法核实时是否明确说明不确定性
- [ ] 对有分歧或重大取舍的结论，是否给出依据、风险和替代解释，且没有为了反对而反对
- [ ] 新增依赖是否优于现有能力或简单实现，并完成维护/安全/许可证/平台评估
- [ ] 删除兼容路径是否有调用方、公共契约、存量数据、迁移和回滚证据
- [ ] 是否先形成可验证的端到端闭环，模块边界是否服务当前职责而非假想未来
- [ ] workaround 是否有明确范围、验证和退出条件
- [ ] 是否先追踪真实调用方、错误路径、测试和公共契约，再提出删除、合并或简化
- [ ] 是否存在可直接复用的项目实现、标准库、平台能力或现有依赖
- [ ] 简化建议是否错误移除了信任边界、数据保护、错误可见性、安全、可访问性、迁移或审计证据
- [ ] 是否需要更新文档/测试

## 发现质量与相关位置

- 每条缺陷写明具体位置、触发输入或状态、可观察后果；沿上游调用方和下游消费者核对，检查现有校验、类型约束、捕获或平台默认是否已经阻止它。
- 严重程度对应真实可达的影响。证据不足的推断标为待核实建议，不能直接升级为严重缺陷。维护者有意改变行为时，先核对需求和兼容约定，再判断是否违反契约。
- 某个修复针对可重复的根因模式时，检查相关模块中的同类调用，区分仍有缺陷、已有保护和未核实；不把局部搜索报告成全库修复，也不扩大为无关重构。
- 零发现是有效结果，不为凑数量编造问题。只读审查交付发现；用户已授权修复时继续必要修复与验证，不自动附带提交、发布或其他外部动作。

## CLI 与安装产物

只在改动涉及相应入口时检查：CLI 的参数、退出码、stdout/stderr、JSON 输出、非交互输入及配置优先级。源码调用成功不能替代用户实际命令或安装入口；涉及删除/清理等操作时，在隔离样例核对预览和执行目标、路径边界及部分失败结果。

Skill、插件、清单或安装器改动需核查实际分发包是否包含引用的脚本/资料，能否从安装目录解析，是否混入缓存或私有文件。用户要求交付可安装产物时，使用隔离配置做适用安装冒烟；普通源码审查只核对证据缺口，不自动进行全局安装。可用时按 `skill-factory` 的安装验收参考或 `desktop-release` 的桌面流程补充，缺少运行条件就明确未验证。
