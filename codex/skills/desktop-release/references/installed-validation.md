# 安装包与运行验收

按实际应用形态选择检查；纯 Python 应用不需要 Electron 检查，纯 Electron 应用不需要 Python 检查。每项记录 `passed / failed / not_run / not_applicable`，并关联具体产物及证据。

## 打包内容

| 对象 | 需要查证的事实 |
| --- | --- |
| Electron main/preload/renderer | 实际入口指向本次产物，preload 与 IPC 可调用，renderer 加载随包资源，不依赖开发服务器或开发绝对路径 |
| asar / extraResources | 动态资源存在于正确位置；需要真实文件系统路径的可执行文件/原生模块正确解包；生产路径按项目约定解析 |
| Python 应用或 sidecar | 可执行文件、动态导入模块、数据文件、必要 DLL/运行库齐全；Electron 调用的是随包组件而不是 PATH 上的开发 Python |
| 外部模型/模板/默认配置 | 必要资源或声明的首次下载路径可用，版本/校验值明确；检查文件内容而不仅是文件名 |
| 原生依赖 | 目标 OS/架构正确，适用的 Node/Electron ABI 与 Python 运行库匹配；在对应目标上验证 |
| 本地数据 | 用户可写数据使用项目用户目录；没有把开发数据库、真实用户资料、密钥或会话凭据误装进包 |

Electron 与 Python 组件共享本次 `run_id` 或有明确的组件构建映射。Python 组件首次启动成功还不足以证明延迟导入的功能齐全，应执行实际依赖这些模块的关键操作。

核查打包允许清单与最终内容是否混入本地日志、测试截图、缓存或私有现场文件；按项目真实需要判断，不机械排除 Python 运行所需字节码或声明的样例资源。新引用的模板、脚本和许可应随本次包可达。

## 安装与启动

使用临时 VM、测试账户或项目已有隔离环境。不要为了验收而覆盖用户正在使用的软件或操作真实业务数据。解包目录可用于早期排错，但不能替代实际安装器验证。

1. 记录最终安装包路径和 SHA-256；检查安装退出状态及安装后的文件。
2. 从明确的安装后路径启动，记录 PID、可执行路径、构建编号和 UI/日志证据。验证单实例锁是否把启动请求转交给旧进程，不能仅凭窗口已出现判定新版本启动。
3. 使用隔离的用户数据、端口与测试资源；确认旧后台服务没有冒充随包服务。若应用无法隔离，先采用 VM 或测试账户，不擅自终止用户工作进程。
4. 核实 Electron → preload/IPC → Python/worker → 结果显示的适用链路；独立 Python 桌面软件则核实其实际 GUI 与业务链路。
5. 执行“本次改动纳入清单”对应的行为检查，以及受影响的关键回归。界面版本文字或源码哈希证明身份，不证明功能正确。
6. 正常退出，确认本次创建的子进程结束，日志可读。只清理本次拥有的测试进程和数据。

在没有开发用 Node/Python、源码目录或虚拟环境的目标环境测试自包含软件。若软件声明依赖系统运行库或外部服务，按其真实支持条件测试并记录，不能额外承诺离线运行。CI GUI 会话不可用时标记安装运行验证缺失，并转到有交互桌面的测试环境。

本次改动涉及快捷方式、命令包装器、文件关联或深链时，再从对应的用户入口验证；直接运行安装目录中的可执行文件不能证明这些入口正确。带 CLI 的软件按受影响部分检查参数、退出码、机器输出和非交互行为，不把开发目录调用当作安装版验收。

## 升级、签名与交付

- 首次安装与旧版本升级分开验证。需要覆盖安装/自动更新时，使用旧版测试数据确认保留、迁移和配置行为。版本回退是否可行取决于数据兼容性，不以“保留旧安装包”代替回滚验证。
- 项目要求签名时，验收最终签名产物的签名状态、发布者及适用时间戳。打包授权不允许擅自获取凭据；只使用已有授权的签名机制，证据中不保存秘密值。
- 自动更新项目核对更新元数据中的版本、文件引用、摘要与实际交付包；本地准备不等于已推送更新渠道。
- 安装包验收后若重签名/改包，新的 SHA-256 需要重新绑定和验收。不能把未签名包的安装记录挂到另一个签名包上。

## 故障定位顺序

先核对“源码快照 → 组件产物 → 安装包 → 运行进程”四个身份，再查资源/环境与功能。这样能区分未纳入改动、构建残留、封装遗漏、安装未更新及新代码本身的缺陷。保留首个有效错误，不靠反复重打覆盖证据。
