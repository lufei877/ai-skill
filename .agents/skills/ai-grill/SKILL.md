# /grill — 需求拷问

> 灵感来源：grill-me skill。核心理念：模糊的需求产出模糊的代码。
> 定位：/plan 的前置步骤。轻量场景独立使用，复杂场景接 /plan。

## 什么时候用

- 用户给出的需求不够具体（缺少边界、约束、验收标准）
- 用户明确要求访谈或梳理需求
- 存在会改变目标、公共契约、数据安全或不可逆操作的重要缺口；不按句式或假设数量触发

## 流程

### 1. 复述理解

用一句话复述你对需求的理解，暴露你的初始假设。

### 2. 逐个拷问

先检查现有代码与文档，只围绕仍缺失的关键维度提问。独立且简短的问题可以合并；给推荐答案并说明依据，不重复询问已有决定。

**功能边界**
- 这个功能的最小可用版本是什么？
- 哪些是必须有的，哪些是"有了更好"？
- 有没有明确不做的事情？

**用户/场景**
- 谁会用这个功能？什么场景下用？
- 输入是什么格式/来源？输出期望是什么？
- 有没有需要处理的边界情况？

**技术约束**
- 有没有必须用或不能用的技术/库？
- 有没有性能要求（响应时间、数据量）？
- 需要兼容什么环境？

**已有代码**
- 项目里有没有类似功能可以复用？
- 这个改动会影响哪些已有模块？
- 有没有需要遵守的项目约定？

**验收标准**
- 怎么算"做完了"？
- 需要测试覆盖吗？覆盖到什么程度？
- 有没有具体的验收场景？

### 3. 总结共识

拷问结束后，输出一份结构化总结：

```
## 需求共识

**目标**：一句话
**必须做**：
- ...
**不做**：
- ...
**技术约束**：
- ...
**验收标准**：
- ...
**待确认**：（如果还有不确定项）
- ...
```

### 4. 衔接下一步

- 如果需求已经足够清晰 → 可以直接执行，或用 /plan 拆步骤
- 如果需求复杂（多文件改动、新功能、重构）→ 建议走 /plan 做详细规划
- 如果用户使用 Trellis → 将共识作为 PRD 输入

## 拷问原则

1. **最小关键问题** — 不逐项审问已经明确的内容，低风险实现细节按项目习惯推进
2. **给推荐答案** — 每个问题附带你基于上下文的推荐，用户确认或修改
3. **适可而止** — 当核心维度都覆盖了就停，不要为了问而问
4. **能查就不问** — 如果答案可以从代码库或文档中获取，先查再问
5. **记录不确定** — 拷问后仍然不确定的项，显式列在"待确认"里

## 与其他工具的配合

- **ACE / 代码搜索**：拷问中涉及"已有代码"维度时，先搜再问
- **smart-search / 外部搜索**：涉及技术选型、最佳实践时，先查再问
- **Trellis**：拷问产出的共识可直接作为 Trellis brainstorm 或 PRD 的输入
- **/plan**：拷问完成后自然衔接 /plan 的步骤拆解

## 输出契约

给出目标、关键边界、验收标准及尚待决定的问题；已有清晰需求时直接说明并结束澄清。
