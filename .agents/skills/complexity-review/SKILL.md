# 复杂度与过度设计审查

## 适用边界

只审查实现是否承担了当前需求不需要的复杂度。普通代码审查仍由 code-review 负责；正确性、安全、性能、迁移和测试问题不能因为本审查追求简化而省略。

## 审查方法

1. 先确认当前需求、真实调用链、错误路径、测试、配置和公共契约，再判断哪些内容不需要。
2. 依次检查：需求是否已由现有行为满足、项目已有实现、标准库、平台/框架原生能力、现有依赖、边界清晰的局部实现；最后才考虑新增依赖、抽象或框架。
3. 查找没有当前调用方的预留接口、只有一个实现却无变化证据的抽象、重复事实、重复配置、包装层和为假想未来建立的扩展点。
4. 每个简化建议说明当前证据、影响范围和验证方法。文件少、代码短或删除量大本身不是收益证据。
5. 没有足够证据时标记为待核实，不把偏好写成缺陷，也不直接修改只读审查范围内的文件。

## 保护边界

不得为了缩短实现而移除或弱化：

- 信任边界校验、安全控制和敏感信息保护；
- 数据完整性、数据丢失保护和必要的错误可见性；
- 并发、资源释放、可访问性或硬件校准要求；
- 公共 API、存量数据、迁移与回滚路径；
- 用户明确要求的行为；
- 发布、验收、审计和工作流依赖的状态与证据。

需要暂时保留的复杂度只有在原因和退出条件已验证时才记录为项目知识，按 project-knowledge-evolution 归入项目决策，不建立第二套债务账本。

## 输出契约

按影响排序输出可定位的简化候选，并分别说明“删除或合并什么、可复用什么、必须保留什么、如何验证”。没有可靠候选时明确说明检查范围与证据限制；本审查不单独宣称实现正确、安全或可发布。
