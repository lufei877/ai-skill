# /finish — 任务收尾

> 对标 Trellis 的 check + finish-work。确保每次任务有闭环。

## 什么时候用

- 完成了一个编码任务，准备告诉用户"做完了"
- 用户说"收尾一下" / "总结一下"
- 任何你认为任务已经完成的时刻（可被 instinct verify-before-commit 触发）

## 流程

### 1. 自检（Check）

按 `constraints.md` 的自检清单逐项检查：

- [ ] 改动范围 = 需求范围（没有多余改动）
- [ ] 样式符合项目与框架约定
- [ ] 没有静默吞掉异常或重复记录同一错误
- [ ] 没有破坏已有调用关系
- [ ] 需要同步的文档/测试已更新
- [ ] 没有 debug 代码残留
- [ ] 冻结区文件未被修改

如果有项目级自检清单（`.ai-skill/project/zones.md` 或项目原有规则），一并执行。

### 2. 验证（Verify）

- 按改动风险运行必要测试；低影响改动可使用适当的静态或人工检查
- 运行构建命令确认无报错（如果适用）
- 没有跑验证就不能声称验证通过 — 如果无法运行，显式说明
- 收尾时检查改动是否具备提交条件，但不自动提交未授权的改动

### 3. 交付总结（Summary）

输出结构化总结：

```
## 完成总结

**改了什么**：
- [文件路径] — 改动说明
- [文件路径] — 改动说明

**验证了什么**：
- [x] 测试通过 / [ ] 未运行测试（原因：...）
- [x] 构建成功 / [ ] 未运行构建（原因：...）
- [x] 其他验证方式（说明）

**剩余风险**：
- ... （如果有）
- 无 （如果没有）
```

### 4. 进化判断（Evolve）

使用原生 `$project-knowledge-evolution`，对照 `evolution/protocol.md` 的证据门槛：

- 已验证 Bug、根因和修复 → 更新项目 pitfalls
- 已验证可重复流程 → 更新项目 recipes
- 用户明确偏好或重复行为证据 → 更新 preferences
- 产品/架构决定 → 更新 decisions
- 多项目重复验证 → 建议上提中央 skill

符合门槛的项目知识直接更新并在交付中简短报告；没有持久价值时不改文件。新增独立 skill 或上提中央规则前告知用户。

### 5. 清理

- 确认没有遗留的临时文件
- 保留验证修复所需的回归测试，清理无用途的调试产物，不为常规清理重复询问

## 与其他工具的配合

- **Trellis**：如果项目使用 Trellis，本流程对应 trellis-check + finish-work
- **Git**：总结输出可直接作为 commit message 的基础
- **/review**：如果改动较大，建议在 /finish 之前先跑 /review

## 输出契约

说明改动、验证结果、剩余风险及有持久价值的知识变更；结论严格对应实际执行证据。
