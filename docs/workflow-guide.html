1如何配置 — 一条命令复制到任意项目

前提条件

确保你的 ai-skill 仓库在固定位置（以下示例假设路径为 /path/to/ai-skill，请替换成你的实际路径）。

一键初始化（推荐）

在你想启用 ai-skill 的项目目录中运行：

# 初始化当前目录（生成所有 IDE 的配置文件）
python "/path/to/ai-skill/scripts/init-project.py" --path .

这条命令会在项目根目录生成以下文件：

生成的文件谁读它加载方式
RULES.md所有 AI 工具通用手动告知 / 被其他文件引用
CLAUDE.mdClaude Code自动加载
.cursorrulesCursor自动加载
AGENTS.mdOpenAI Codex自动加载
.windsurf/rules/ai-skill.mdWindsurf自动加载
.github/copilot-instructions.mdGitHub Copilot自动加载
.kiro/rules/ai-skill.mdKiro自动加载
GEMINI.mdGemini Code Assist自动加载

只初始化特定 IDE

# 只为 Cursor 生成配置
python "/path/to/ai-skill/scripts/init-project.py" --path . --ide cursor

# 只为 Claude Code 生成配置
python "/path/to/ai-skill/scripts/init-project.py" --path . --ide claude-code

# 只为 Codex 生成配置
python "/path/to/ai-skill/scripts/init-project.py" --path . --ide codex

# 可选值: cursor | claude-code | codex | windsurf | copilot | kiro | gemini | all

规则更新后同步

当你修改了 ai-skill 仓库里的规则（比如加了新 instinct），对项目重新跑一次 init 即可同步：

# 在项目目录下，重新初始化 = 同步最新规则
python "/path/to/ai-skill/scripts/init-project.py" --path .
Tip：建议把 init 命令加入你的项目初始化脚本或 Makefile，这样 clone 后一键就位。

2各 IDE 的配置细节

Cursor

零配置 初始化后即生效

Cursor 自动读取项目根目录的 .cursorrules，里面已包含完整的 RULES.md 内容。

MCP 工具（ACE、smart-search-cli）在 Cursor Settings → MCP 中单独配置：

// Cursor Settings → MCP → 添加 Server
{
  "mcpServers": {
    "ace": {
      "command": "ace-mcp",
      "args": ["--workspace", "."]
    },
    "smart-search": {
      "command": "smart-search-cli",
      "args": ["mcp"]
    }
  }
}

Claude Code

自动 + Hooks 推荐配置 hooks 增强

Claude Code 自动读取 CLAUDE.md。推荐额外配置 hooks：

# 在项目根目录
mkdir .claude
copy "/path/to/ai-skill\hooks\claude-code\settings.json" ".claude\settings.json"

hooks 会在你每次编辑文件时自动提醒检查冻结区和自检清单。

OpenAI Codex

零配置 AGENTS.md 自动生效

Codex 自动读取项目根目录的 AGENTS.md。规则和工作流完全生效。

Codex 目前不支持 MCP，搜索能力受限于其内置工具。但 /grill、/plan、/finish 的工作流指令依然有效。

注意：各 IDE 的 MCP 工具配置互相独立。ai-skill 只管规则层，MCP 工具需要在各 IDE 中单独安装和配置。

3四阶段工作流怎么用

Phase 0: /grill — 拷问需求
把模糊想法问清楚。AI 一次一个问题拷问你，产出结构化的需求共识。
适用于：需求不够具体、新功能、你说"大概想做一个..."时。
Phase 1: /plan — 规划步骤
把需求拆成可验证的步骤。每步带验证方式 + 风险评估。
适用于：多文件改动、涉及公共接口、需要分步实施时。
Phase 2: 执行
AI 按计划编码。期间 instincts 自动生效：先搜再改、大改动前确认、匹配已有风格。
你只需要确认 AI 的提问和阶段性结果。
Phase 3: /finish — 收尾闭环
自检清单 → 跑测试验证 → 交付总结（改了什么、验证了什么、剩余风险）→ 进化判断。
确保每次任务有完整闭环，不遗留问题。
什么时候跳过阶段？
任务复杂度建议流程示例
简单（<5 min）直接执行"把这个变量名改一下"
中等/grill → 执行 → /finish"加一个缓存层"
复杂/grill → /plan → 执行 → /finish"迁移到 GraphQL"
高风险/grill → /plan → /review → 执行 → /finish"重构认证模块"

## 需求共识

**目标**：启动时加载本地插件，通过 hook 机制扩展已有流程
**必须做**：

5先搜再改 + Smart Search 使用方法

instinct: search-before-code（自动生效）

这是一个 Always-On 的行为本能，AI 在动手写代码之前会自动判断需要什么信息，然后选择正确的搜索方式。你不需要告诉它——它自动做。

信息源路由规则
需要什么用什么搜典型场景
明确符号
函数名、类名、变量名		 grep / glob
精确匹配		 找 handleSubmit 在哪定义的
语义理解
相关模块、调用链、复用		 ACE 或同类工具
代码库级		 "支付相关的代码在哪几个模块？"
外部资料
库文档、API、最佳实践		 smart-search-cli
外部搜索		 "Prisma 5.x 怎么做 batch upsert？"

smart-search-cli 怎么配置

# 1. 安装（如果还没装）
npm install -g smart-search-cli

# 2. 在 Cursor 中配置 MCP
# Settings → MCP → 添加：
{
  "mcpServers": {
    "smart-search": {
      "command": "smart-search-cli",
      "args": ["mcp"]
    }
  }
}

# 3. 在 Claude Code 中配置 MCP
# .claude/settings.json 或全局 settings 中添加：
{
  "mcpServers": {
    "smart-search": {
      "command": "smart-search-cli",
      "args": ["mcp"]
    }
  }
}

smart-search 使用场景

你
帮我用 Bun 的 SQLite 驱动实现连接池
AI
[instinct "先搜再改" 触发]

1. 先搜项目里有没有已有的数据库连接代码...
→ grep "sqlite" / ACE 查数据库模块

2. Bun 的 SQLite 驱动是否支持连接池是外部问题...
→ smart-search "bun sqlite connection pool 2024"

3. 搜索结果：Bun 内置的 bun:sqlite 是同步的、单连接的，不需要也不支持传统连接池。但可以用 worker 做并发。

基于这个信息，我建议的方案是...

什么时候 AI 会自动用 smart-search？

  • 涉及第三方库的具体 API 用法（尤其是新版本）
  • 需要确认当前最佳实践（不确定自己的知识是否过时）
  • 用户提到了一个它不熟悉的技术/工具
  • 技术选型比较（A 和 B 哪个更适合）
Codex 用户注意：Codex 目前不支持 MCP，所以 smart-search 和 ACE 不可用。AI 会依赖自身知识 + Codex 内置搜索。规则中的 "先搜再改" instinct 会退化为用 grep/glob 做基础搜索。

6完整使用实例

实例：给项目加一个 Rate Limiter

Phase 0 /grill
你：/grill 我想给 API 加限流

AI 拷问（约 8 个问题）：
- 限流粒度？→ 每个用户（by API key）
- 限流窗口？→ 滑动窗口，1 分钟
- 限流阈值？→ 60 次/分钟，可配置
- 超限响应？→ 429 + Retry-After header
- 存储？→ Redis（已有实例）
- 要不要区分 endpoint？→ 不用，统一限制
- 白名单？→ 内部服务 IP 跳过
- 已有中间件？→ 有 Express middleware 架子

产出：需求共识文档
Phase 1 /plan
AI 规划：
1. 创建 src/middleware/rate-limiter.ts
   → 验证: 单元测试覆盖正常/超限/白名单场景
2. 在 src/app.ts 注册中间件
   → 验证: curl 连续请求 61 次，第 61 次返回 429
3. 添加配置项到 config/default.ts
   → 验证: 修改配置后限流阈值生效

风险：需要确认 Redis 连接是否已在 app 初始化时建立
Phase 2 执行
AI 自动行为：
[search-before-code] 先搜项目已有的 middleware 写法 → 发现统一用 class 形式
[search-before-code] 搜 Redis client 在哪初始化 → src/lib/redis.ts 已有单例
[match-existing-style] 匹配已有 middleware 的 constructor 注入模式
[ask-before-big-change] 要改 app.ts 注册链 → 告知用户具体改动

然后开始写代码...
Phase 3 /finish
AI 输出：
## 完成总结

**改了什么**：
- src/middleware/rate-limiter.ts — 新增滑动窗口限流中间件
- src/app.ts (L23) — 注册 RateLimiter 中间件
- config/default.ts (L41-44) — 新增 rateLimit 配置段
- tests/rate-limiter.test.ts — 3 个测试用例

**验证了什么**：
- [x] 单元测试 3/3 通过
- [x] 手动 curl 验证 429 + Retry-After

**剩余风险**：
- Redis 断连时的降级策略未实现（当前会 500）

**进化判断**：
- 建议记录 recipe: "Express + Redis 滑动窗口限流标准实现"
