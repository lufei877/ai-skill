# /review — 代码审查

## 流程

### 1. 收集变更
- 查看 `git diff` 或用户指定的文件
- 理解变更的目的（修 bug？加功能？重构？）

### 2. 逐项检查
按 `code-review` 的完整标准复核发现质量、调用链保护与适用的安装/CLI 入口；下面的维度用于组织审查，不另行启动第二套流程。

按以下维度审查：

**正确性**
- [ ] 逻辑是否正确，边界条件是否处理
- [ ] 是否有 off-by-one、空值、竞态条件

**安全性**
- [ ] 有无注入风险（SQL、XSS、命令注入）
- [ ] 有无硬编码密钥
- [ ] 用户输入是否校验

**精准手术（Karpathy 原则三）**
- [ ] 改动是否超出需求范围
- [ ] 有无顺手改的格式/风格/注释
- [ ] 每行改动能追溯到用户请求吗

**极简优先（Karpathy 原则二）**
- [ ] 有无过度抽象或投机性功能
- [ ] 代码量是否可以更少

**质量**
- [ ] 命名是否清晰
- [ ] 错误处理是否完整
- [ ] 是否需要测试覆盖

### 3. 输出报告
```
## Review 结果

**总体**: PASS / PASS WITH COMMENTS / NEEDS CHANGES

### 必须修改
- ...

### 建议修改
- ...

### 亮点
- ...
```

## 输出契约

交付按严重程度排序的审查发现、文件位置、影响和证据；说明审查范围与未执行的验证，无问题时明确报告。
